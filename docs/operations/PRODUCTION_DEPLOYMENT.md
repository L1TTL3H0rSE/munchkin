# Production deployment

This runbook describes the reviewed local delivery boundary for
`munchkin.l1ttl3h0rse.ru`. It does not authorize Terraform apply, GitHub
environment changes, Timeweb NS changes, Lockbox payload insertion, VM
bootstrap or a first production rollout.

## Fixed release contract

- Branch: `main` only.
- Release input: full lowercase commit SHA plus the verified immutable game and
  web references from the dependency plan.
- First maintenance window: `2026-08-02 09:00–11:00 Europe/Moscow`.
- Public edge: Traefik only on TCP `80/443`; game, web, PostgreSQL, OTLP and
  management ports remain private.
- Administration: owner/admin SSH stays on TCP `22` and is restricted to the
  owner CIDR set. GitHub delivery uses public TCP `2222`, where only the
  forced-command `munchkin-deploy` identity is eligible.
- Migration contract: `health-migrations-v1`; `AUTO_MIGRATE=false` for the
  long-running game service.
- Evidence artifact:
  `production-release-evidence-<run-id>-<run-attempt>`, retained 30 days.

## Preflight and separate approvals

Before any remote operation, show a sanitized exact mutation plan containing
the target resources, expected adds/changes/destroys, DNS/NS consequence,
secret-store destination, VM commands, rollback and cost/destructive risk.
Obtain a separate approval for each applicable gate:

1. Terraform non-secret DNS/Lockbox/IAM metadata.
2. GitHub `production-deploy` environment and protected variables/secrets.
3. Timeweb authoritative NS delegation and the resulting DNS record.
4. Lockbox payload and owner-side secret-store insertion.
5. Production VM bootstrap and first deploy.

No cloud credential, password, private key, owner email or Lockbox payload is
placed in this repository.

Local checks, with credentials removed from the process, are:

```powershell
terraform fmt -check -recursive infra/terraform
& 'C:\Program Files\Git\bin\bash.exe' scripts/terraform-check.sh
docker compose --parallel 8 -f compose.production.yml config --quiet
```

The Compose check needs a Docker daemon. The repository verifier remains the
canonical lifecycle gate. A missing daemon is recorded as an environment
limitation, not as successful runtime evidence.

## Host preparation

The owner supplies a single ED25519 public key to
`scripts/production/bootstrap-host.sh --deploy-public-key-file PATH` through a
protected process-local file. The script creates the dedicated
`munchkin-deploy` user, removes Docker-group membership, installs the forced
command gateway and creates root-owned `/srv/munchkin` directories. It accepts
no private key or secret payload.

The host source install copies the production Compose, Traefik, Collector and
allowlisted scripts into `/srv/munchkin/compose`. The systemd unit recovers
the stack after Docker, network and the mounted data disk are available.
The same bootstrap installs and runs `configure-deploy-ssh.sh`: it validates
the candidate and assembled OpenSSH configuration before reload, explicitly
retains TCP `22`, adds deploy-only TCP `2222`, and applies a UFW rate limit.
Failure restores the prior sshd drop-in before returning an error.

Required root-only files are created by the owner-side secret procedure:

| Path | Required entries | Mode |
|---|---|---:|
| `/srv/munchkin/secrets/postgres.env` | `POSTGRES_PASSWORD` | `0600` |
| `/srv/munchkin/secrets/game.env` | `DATABASE_URL` | `0600` |
| `/srv/munchkin/secrets/traefik.env` | `ACME_EMAIL`, `ACME_CA_SERVER` | `0600` |
| `/srv/munchkin/traefik/acme/acme.json` | ACME account state | `0600` |

## Controlled rollout

After `publish` succeeds on `main`, CI passes its exact image outputs, SHA and
run ID to the reusable deploy workflow. Existing `production-images` and
`production-deploy` manual approvals remain in force. The protected deploy
workflow validates image digests and the full SHA, reuses the existing pinned
SSH host key through `HostKeyAlias`, connects only on TCP `2222`, and sends
only the allowlisted `deploy` command. Manual `workflow_dispatch` remains
available for reviewed recovery. The host script:

1. Takes a serialized deployment lock and validates secret-file ownership and
   modes without printing values.
2. Runs `docker compose --parallel 8 ... config --quiet` and pulls the
   immutable game/web pair.
3. Starts PostgreSQL and runs the one-shot migration.
4. Starts game, web and Traefik, then waits for game readiness, web health and
   the Traefik ping.
5. Runs internal and public HTTPS smoke checks.
6. Writes failed evidence without changing the current release, or atomically
   updates `current-release.json` and `previous-release.json` on success.

The exact remote workflow command is generated by
`.github/workflows/deploy-production.yml`; do not replace it with an ad-hoc
SSH shell. A readiness timeout or migration failure aborts the rollout.

Do not rewrite the known-hosts secret as `[host]:2222`. `HostKeyAlias` keeps
the existing pinned host identity authoritative on the non-standard port.

## ACME sequence

Use the owner-supplied email only in the protected host secret file. First set
`ACME_CA_SERVER` to the Let's Encrypt staging endpoint, verify DNS delegation,
HTTP-to-HTTPS behavior and certificate hostname/chain, then record the
staging smoke result. Only after that approval set the production endpoint and
repeat the controlled deployment. Keep the root-only ACME file across restarts
and do not commit or upload its contents.

## Recovery

After a reboot, verify the data disk mount, Docker, the systemd unit and
`scripts/production/status.sh`. The recovery path loads the last successful
immutable pair and repeats migration/readiness/smoke through the same root
boundary. Rollback rules are in
[`PRODUCTION_ROLLBACK.md`](PRODUCTION_ROLLBACK.md).
